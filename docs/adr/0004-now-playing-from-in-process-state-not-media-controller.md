一覧の聴いている回のマークとミニプレイヤーは「聴いている回」を知る必要があるが、これらの画面では Media3 の正規の経路である `MediaController` の購読は採らない。`MediaController` を作ると `PlaybackService` に bind してサービスが起動するため、番組一覧を開くだけで再生サービスが立ち上がり、「何も載っていなければ出さない」判定が起動と競合する。代わりに、`PlaybackService` が `Player.Listener` で書き込むプロセス内のシングルトン `NowPlaying`（同期が削除の対象から外す回を知るのにも使う）を UI が読む。再生／一時停止などの**操作**だけは `MediaController` を使う（ミニプレイヤーが見えている時点でサービスは生きているので、新たな起動にはならない）。仕組み（利用者の数え方、再開、Android Auto との関わり）は `docs/architecture/playback.md` の「聴いている回の読み方」節。

- `MediaController` はサービスに bind するので、持っている限り `stopSelf()` してもサービスは破棄されない。プロセスの寿命で持つと、一時停止してタスクを消してもサービスが止まらず、聴いている回が消えない。そのため操作のために持つ `MediaController` は、使い終わったら手放す
- 範囲: 一覧とミニプレイヤーの**読み**だけ。再生画面は再生を始める画面なのでサービスが生きていて当然で、位置の追従も要るため `MediaController` を購読する
- 前提: アプリは単一のプロセスで、Service・Worker・UI が同じ `NowPlaying` のインスタンスを見る。マルチプロセスにするときはこの決定を見直す
- Android Auto は車載機からアプリの外でサービスに bind するので、UI を開かずにサービスが起動する。プレイヤーが空のあいだ `NowPlaying` は null のままなので、一覧とミニプレイヤーの「何も載っていなければ出さない」判定は変わらない
- プロセスが死んだ後の再開（通知の ▶、Auto の「最近」、端末の再起動の後）は、Room の再生位置の記録から組み立て直す。Room に「聴いている回」を書くのではなく、復元した回がプレイヤーに載った時点で「聴いている回」が立つ

## 退けた案

- **`MediaController` の購読** — Media3 の想定する形で、別のプロセスやほかのアプリのセッションにも使えるが、上の起動の副作用がある
- **Room に「聴いている回」を書く** — プロセスが死んだ後も残ってしまい、「サービスが止まれば消える」という意味と合わない
