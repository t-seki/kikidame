番組と各回を取ってくる先を「**取得元 (Source)**」と呼び、Jellyfin のライブラリに加えて、利用者が選んだ「**共有フォルダ (Shared Folder)**」（NAS の SMB の共有、端末のフォルダ）を取得元にできるようにする。録音を NAS（SMB の共有）に溜めているが Jellyfin は立てていない人にも、入口を作るためである。

## 決定

1. **用語**: 取得元は Jellyfin のライブラリ（音楽かブック。ブックは ADR 0010）か共有フォルダのどちらか。取得元の中で番組・各回を指す ID（ADR 0001 の `sourceItemId`）は、取得元の種類によらず「**取得元 ID (Source Item ID)**」と呼ぶ（CONTEXT.md）
2. **取得元は同時に 1 つ**。別の取得元に変えるときは、手元の番組・各回・再生位置・ファイル（番組の画像のファイルも）をすべて消してやり直す。文言は「取得元を変える」。取得元をまたいで再生位置を引き継ぐ仕組み（Jellyfin と共有フォルダの間の突合）は作らない。同じ Jellyfin のサーバとユーザーのままライブラリだけを変えるのは「取得元を変える」に当たらない（ADR 0010 の決定 7）
3. **初回の画面で取得元を選ぶ**: 「Jellyfin に接続」「NAS の共有フォルダ（SMB）」「端末のフォルダ」から 1 つ
4. **つなぎ方**: SMB はアプリに組み込む（smbj）。端末のフォルダは Storage Access Framework（SAF）で選ぶ。NFS と WebDAV は対象外
5. **共有フォルダの構成**: 中はちょうど `<配信元>/<番組>/<各回のファイル>` の 3 段。3 段目にある音声ファイル（拡張子で判定: m4a、mp3、aac、ogg、opus、flac、wav）だけを各回とし、それ以外（2 段目以下・4 段目以上のファイル、音声でないファイル）は黙って無視する。ただし番組のフォルダ（2 段目）の `folder.jpg` だけは、番組の画像（CONTEXT.md）として読む（ADR 0009）。配信元と番組はフォルダの名前で決め、タグは使わない。名前が `.`・`@`・`#` で始まるフォルダとファイル（NAS や OS が作るもの）は、どの段でも無視する
6. **取得元には書き込まない**: アプリは取得元を読むだけで、書き込みも削除もしない。例外は 1 つだけで、取得元が Jellyfin の**ブック**のライブラリのとき、再生の共有のために各回の UserData（再生位置と再生済み）を書く（ADR 0010 の決定 3）。音声のファイルや、Jellyfin の音楽のライブラリ・共有フォルダには何も書かない。保持ルールで消すのは、アプリの領域にコピーしたファイルだけ。SMB と端末のフォルダも、Jellyfin と同じくアプリの領域にコピーしてから再生する
7. **取得元 ID**: Jellyfin では Jellyfin の id（ブックのライブラリの番組は ADR 0010 の決定 2）。共有フォルダでは共有フォルダの中の相対パス（番組は `<配信元>/<番組>`、各回は `<配信元>/<番組>/<ファイル名>`）。ファイル名を変えると未結合になり、突合（ADR 0001。同じ番組の中のタイトル → 公開日と尺）で結び直す。番組のフォルダ名を変えると、（配信元, 番組名）で結べないので消失（判断保留）になる
8. **回の情報はタグから読む**: 新しいファイル、またはパス・大きさ・更新日時のどれかが変わったファイルのときだけタグを読み、結果を回の行に持つ。それ以外のファイルは、同期のたびに一覧（名前・大きさ・更新日時）を取るだけにする
9. **タグが無いときの補い方**: タイトルはタグの title、無ければ拡張子を除いたファイル名。公開日はタグの日付（年月日まであるとき）、無ければ取り込み日時で代用する。取り込み日時は、共有フォルダではファイルの更新日時。尺は音声から取り、取れなければ不明（突合の第 2 段の対象外）。出演者はタグの artist、無ければ空
10. **「Wi-Fi のみ」**: 取得元によらず同じ条件（Wi-Fi のみなら UNMETERED、そうでなければ CONNECTED。`SyncScheduler`）。例外として、取得元が端末のフォルダのときはネットワークの条件をかけない（NOT_REQUIRED。端末の中から端末の中へのコピーなので）

## 理由

- **SMB をアプリに組み込む（4）**: SMB を SAF に出す現役のアプリは、CIFS Documents Provider（最終リリース 2025-05、SMB3 の暗号化に未対応）と RSAF（rclone 経由）くらいしか見つからなかった。smbj（`com.hierynomus:smbj`）は Apache-2.0、0.15.0（2026-08-21）、SMB2/3 対応、BouncyCastle に依存し、Material Files・CIFS Documents Provider・SambaLite が Android で使っている
- **NFS を対象外にする（4）**: NFS を SAF に出すアプリは見つからず、Android に組み込める現役の NFS クライアントのライブラリも見つからなかった（nfs4j はサーバの実装、EMC nfs-client-java は 2022 年で止まっている）
- **端末のフォルダを SAF で選ぶ（4）**: SAF の永続権限は再起動の後も残り、1 アプリあたり 512 件（上限を超えると古いものから外れる）。対象の移動・削除、アプリのデータの消去で失効する（AOSP `UriGrantsManagerService.java` の `MAX_PERSISTED_URI_GRANTS`、Android Developers の documents-files のページ）
- **ローカルネットワークへの接続**: LAN の中のサーバへの接続に要る `ACCESS_LOCAL_NETWORK`（Android 17+）は宣言している（`app/src/main/AndroidManifest.xml`）。SMB の接続がこの権限だけで足りるかは未確認
- **構成をちょうど 3 段にし、タグで番組を決めない（5）**: 番組と配信元を、フォルダの構成ではなくタグ（album = 番組、albumartist = 配信元）で決める案と、`<番組>/<各回のファイル>` の 2 段も認める案を比べ、どちらも採らなかった
  - 主な radiko の録音ツールでは、番組がファイル名にしか無い。radigo・rec_radiko_ts・radish は 1 つのフォルダに `<局 ID>_<日時>` のような名前で書き出し、タグを付けない（各ツールのソース）。Radikool は `<局コード>/<番組名>_<日付>.mp3` の形で書き出す（airshelf の要件書の観測と、既定の書式についての二次情報。既定の書式は未確認）。タグで決めても 2 段を認めても、これらの人は使えるようにならない
  - タグの入れ方はツールごとに違い、決まった読み方では番組と配信元が取れない。らじれこは album に局を入れ（観測）、Radikool は局を genre に入れる（観測）。タグを優先すると、3 段で使えているらじれこの利用者の番組が局ごとにまとまってしまう
  - 2 段を認めて使えるようになるのは、主に Podcast のダウンローダー（gPodder・Podgrab。どちらも `<Podcast 名>/<回>` の 2 段）の利用者で、主に想定する利用者（ラジオの録音を聴く人）から外れる
  - 2 段など別の構成を求める具体的な利用者やツールが現れたら、2 段を認める案から検討する。そのときは、番組とフォルダが 1 対 1 であることに、全走査だけでなく 1 番組の同期（`SharedFolderSource` の `fetchProgram`・`fetchProgramEpisodes`）、取得元 ID（決定 7）、番組の画像（ADR 0009）も依存していることを前提に入れる

## 退けた案

- **NFS・WebDAV も取得元にする** — 対象外（NFS は、上の理由のとおり組み込める現役のライブラリが見つからなかった）
- **取得元を同時に複数持つ、取得元をまたいで再生位置を引き継ぐ** — 作らない（決定 2）
- **取得元への書き込み・削除** — しない（決定 6。ブックのライブラリの UserData の書き込みだけが例外）

## 取得元の境界

- 同期とダウンロードは、取得元の種類に依存しない境界（`core/data` の `data.source.SourceGateway`）だけを通して取得元に触る。Jellyfin はその実装の 1 つ（`JellyfinSource`）で、認証の情報は実装の側で持つ。接続の手順（サインイン、ライブラリの一覧）は Jellyfin の側（`JellyfinGateway`）にある。取得元の種類による切り替えは `SessionSourceGateway`
- 接続は取得元の種類ごとの型（`SessionState.Ready` が `ConnectedSource.Jellyfin`・`ConnectedSource.Smb`・`ConnectedSource.Device` のどれかを持つ）。DataStore のキーは種類ごとに分かれる（Jellyfin のキー、SMB の `smb_*`、端末のフォルダの `device_*`）
- 名前はサーバに依らない形にした（`SourceItemId` / `sourceItemId`、`SourceProgram` / `SourceEpisode` / `SourceSnapshot`、`SourceException`）。Room は版 7 の自動移行（`@RenameColumn` / `@DeleteColumn`）で、列 `serverItemId` を `sourceItemId`（programs・episodes）、`stationName` を `publisherName`、`airedAt` を `publishedAt` に改め、使っていなかった `playback_states.syncedAt` を消した。データは移行で残す
- 取得元の境界には、番組の画像の中身を取る口（`fetchProgramImage`。ADR 0009）と、各回のファイルの大きさを取る口（`fetchFileSize`。読み取りだけで、取得元のファイルには書かない。ADR 0011）もある

## SMB

- SMB の接続は 1 回の操作ごとに張って閉じる
- 依存は smbj（Apache-2.0）と、推移的な asn-one（Apache-2.0）・mbassador（MIT）・bcprov-jdk18on（Bouncy Castle Licence）で、MPL-2.0 で公開する方針（ADR 0005）とは食い違わない（どれも寛容なライセンス。ライセンスは各 POM の記述による）

## 共有フォルダの全走査を番組ごとに取り込む

大きな共有では、全部のファイルの一覧とタグを読み終えてからまとめて取り込む形だと、タグの読み取りの途中で接続が切れたときに何も取り込まれない。そのため共有フォルダの全走査は、次の形にする。決定 8 の「新しいファイル、またはパス・大きさ・更新日時のどれかが変わったファイルのときだけタグを読む」は変わらない。

1. 一覧（名前・大きさ・更新日時）を先に全部取り、番組ごとにタグを読み、その番組を読み終えたら取り込む（取り込みの範囲と、その番組の中での削除・予約は 1 番組の同期と同じ）。全部を読み終えたら、番組の消失の判断と最終同期の時刻の記録を行う（ADR 0003 の削除の権限は変えない）。仮のタイトルで取り込むことはしない。Jellyfin の走査は番組ごとに取り込まない
2. 取り込み済みの回は DB に大きさと更新日時を持つので、次の同期ではタグを読まない。止まって失うのは、読みかけの番組 1 つ分だけ。そのための別の控えは作らない
3. 走る場所はアプリのスコープと WorkManager。前面サービスや通知は作らない
4. 接続が切れたら張り直し、同じファイルから読み直す。続けて 3 回失敗したら、その同期は到達不能で終わる（取り込み済みの番組は残る）
5. タグの読み取りは、ファイルごとに 256 KB ずつまとめて読み、小さな読み出しにはそこから返して往復を減らす。m4a のタグの読み取りは 1 本あたり 2,048 バイトずつ 150〜191 回の読み出しになり、遅いのは転送量ではなく往復の回数と見ている。並列で読むことはしていない
6. タグを読む回がある間、番組一覧に「タグを読み込み中 1,234 / 6,090」のように件数を出す

走査の途中で画面が消えて裏に回ると、しばらくして Android が接続を壊し、張り直しも効かずに到達不能で終わることがある。壊されるまでの時間は一定ではなく、何で決まるかは未確認。取り込み済みの番組は残り、次の同期で続きから読む（上の 2）。

## 端末のフォルダ

1. 端末のフォルダも、ほかの取得元と同じくアプリの領域にコピーしてから再生する（決定 6 のまま、取得元には書き込まない）。その場で再生する形と、元のファイルを消す形は採らない。主に想定する人（PC で録ったファイルを Syncthing-Fork や FolderSync で端末のフォルダに同期して溜めている人）では、消すと同期で元のファイルまで消えるおそれがあり、その場で再生する形は手元のファイルを前提にした箇所の改修が大きいため。走査とダウンロードは、SAF 版の木（`DeviceFolderTree`。`DocumentsContract` で一覧・部分読み・続きからの読み出しをする）を `SharedFolderSource` に乗せる
2. 構成は 3 段のまま（決定 5）。深さを選ばせる仕組みは作らない
3. 選べるのは端末のストレージ（内部ストレージと SD カード）のフォルダだけ。選んだツリーの URI の authority が `com.android.externalstorage.documents` のときだけ受け付け、ほかの provider（Google ドライブ、SAF 経由の SMB など）は選び直させる
4. 取得元が端末のフォルダのときは、ダウンロードと同期（定期・手動）にネットワークの条件をかけない（決定 10 の例外。WorkManager の NOT_REQUIRED で、手動の同期の従量制での中止もかけない）
5. 永続権限が無い・取り消された、または選んだフォルダ（根）が無いと分かったら、未接続（ログアウトの状態）にしてフォルダを選び直させる。「分かった」とするのは、永続権限の一覧に読み取りが無い、provider が `SecurityException` を投げた、根の問い合わせに provider が「無い」（行の無い結果）と答えたときだけで、それ以外の失敗は SMB と同じく通常の失敗（到達不能）に倒す（`DeviceFolderTree` の KDoc）。手元の番組・各回・ファイルは残す（取得元 ID は相対パスなので、選び直したフォルダの中の構成が同じなら結び直る）。根が無いのを「無い」（null）で返すと全番組が消失扱いになるので、例外（`SourceException.Unauthorized`）にする
6. 「取得元を変える」では、持っている永続権限を手放す（`releasePersistableUriPermission`）
7. `ACCESS_LOCAL_NETWORK` は、取得元が Jellyfin か SMB のとき（ログアウト中で前回の取得元が Jellyfin か SMB のときを含む）だけ起動時に要求し、まだ取得元を選んでいない人には取得元の選択で Jellyfin か SMB を選んだときに要求する。端末のフォルダの人には要求しない
8. 選ぶときは、取得元の選択の「端末のフォルダ」から説明の画面（3 段の構成の例と、内部ストレージの直下や Download そのものは選べないこと）を経て、OS のフォルダ選択（`ACTION_OPEN_DOCUMENT_TREE`）を開く。選んだ後は SMB と同じく直下が読めるかだけを確かめて保存する

- 依存は足していない（`DocumentsContract` と `ContentResolver` は SDK の標準）
- SAF の実機の挙動（`Download` の下のサブフォルダを選べるか、SD カードのツリーの URI の形と authority、フォルダの中のファイルが多いときの遅さ）は確かめていない（未確認）
