番組と各回を取ってくる先を「**取得元 (Source)**」と呼び、Jellyfin のライブラリに加えて、利用者が選んだ「**共有フォルダ (Shared Folder)**」（NAS の共有フォルダ（SMB）、端末のフォルダ）を取得元にできるようにする。録音を NAS に溜めているが Jellyfin は立てていない人にも、入口を作るためである。

## 決定

1. **用語**: 取得元は Jellyfin のライブラリ（音楽かブック。ブックは ADR 0010）か共有フォルダのどちらか。取得元の中で番組・各回を指す ID（ADR 0001）は、取得元の種類によらず「**取得元 ID (Source Item ID)**」と呼ぶ（CONTEXT.md）
2. **取得元は同時に 1 つ**。別の取得元に変えるときは、手元の番組・各回・再生位置・ファイル（番組の画像のファイルも）をすべて消してやり直す。文言は「取得元を変える」。取得元をまたいで再生位置を引き継ぐ仕組み（Jellyfin と共有フォルダの間の突合）は作らない。Jellyfin のライブラリだけを選び直すときの扱いは ADR 0010 の決定 7
3. **初回の画面で取得元を選ぶ**: 「Jellyfin に接続」「NAS の共有フォルダ（SMB）」「端末のフォルダ」から 1 つ
4. **つなぎ方**: SMB はアプリに組み込む（smbj）。端末のフォルダは Storage Access Framework（SAF）で選ぶ。NFS と WebDAV は対象外
5. **共有フォルダの構成**: ADR 0013
6. **取得元には書き込まない**: アプリは取得元を読むだけで、書き込みも削除もしない。例外は 1 つだけで、取得元が Jellyfin の**ブック**のライブラリのとき、再生の共有のために各回の UserData（再生位置と再生済み）を書く（ADR 0010 の決定 3）。音声のファイルや、Jellyfin の音楽のライブラリ・共有フォルダには何も書かない。保持ルールで消すのは、アプリの領域にコピーしたファイルだけ。共有フォルダも、Jellyfin と同じくアプリの領域にコピーしてから再生する
7. **取得元 ID**: Jellyfin では Jellyfin の id（ブックのライブラリの番組は ADR 0010 の決定 2）。共有フォルダでは共有フォルダの中の相対パス（番組は `<配信元>/<番組>`、各回は `<配信元>/<番組>/<ファイル名>`）。ファイル名を変えると未結合になり、突合（ADR 0001。同じ番組の中のタイトル → 公開日と尺）で結び直す。番組のフォルダ名を変えると、（配信元, 番組名）で結べないので消失（判断保留）になる
8. **回の情報はタグから読む**: 新しいファイル、またはパス・大きさ・更新日時のどれかが変わったファイルのときだけタグを読み、結果を回の行に持つ。それ以外のファイルは、同期のたびに一覧（名前・大きさ・更新日時）を取るだけにする。全走査を番組ごとに取り込むことは ADR 0003 の決定 4
9. **タグが無いときの補い方**: タイトルはタグの title、無ければ拡張子を除いたファイル名。公開日はタグの日付（年月日まであるとき）、無ければ取り込み日時で代用する。取り込み日時は、共有フォルダではファイルの更新日時。尺は音声から取り、取れなければ不明（突合の第 2 段の対象外）。出演者はタグの artist、無ければ空
10. **「Wi-Fi のみ」**: 取得元によらず同じ条件（Wi-Fi のみなら従量制でない接続、そうでなければ何かの接続）。例外として、取得元が端末のフォルダのときはネットワークの条件をかけない（端末の中から端末の中へのコピーなので）
11. **取得元の境界**: 同期とダウンロードは、取得元の種類に依存しない境界だけを通して取得元に触る。Jellyfin も共有フォルダも、その実装の 1 つ。境界の口と実装は `docs/architecture/fetching.md` の「取得元の境界とセッション」節

## 理由

- **SMB をアプリに組み込む（4）**: SMB を SAF に出す現役のアプリは、CIFS Documents Provider（最終リリース 2025-05、SMB3 の暗号化に未対応）と RSAF（rclone 経由）くらいしか見つからなかった。smbj（`com.hierynomus:smbj`）は Apache-2.0、0.15.0（2026-08-21）、SMB2/3 対応、BouncyCastle に依存し、Material Files・CIFS Documents Provider・SambaLite が Android で使っている
- **NFS を対象外にする（4）**: NFS を SAF に出すアプリは見つからず、Android に組み込める現役の NFS クライアントのライブラリも見つからなかった（nfs4j はサーバの実装、EMC nfs-client-java は 2022 年で止まっている）
- **端末のフォルダを SAF で選ぶ（4）**: SAF の永続権限は再起動の後も残り、1 アプリあたり 512 件（上限を超えると古いものから外れる）。対象の移動・削除、アプリのデータの消去で失効する（AOSP `UriGrantsManagerService.java` の `MAX_PERSISTED_URI_GRANTS`、Android Developers の documents-files のページ）
- **ローカルネットワークへの接続**: SMB の接続が `ACCESS_LOCAL_NETWORK`（「端末のフォルダ」節の 7。仕組みは `docs/architecture/fetching.md`）だけで足りるかは未確認

## 退けた案

- **NFS・WebDAV も取得元にする** — 対象外（NFS は、上の理由のとおり組み込める現役のライブラリが見つからなかった）
- **取得元を同時に複数持つ、取得元をまたいで再生位置を引き継ぐ** — 作らない（決定 2）
- **取得元への書き込み・削除** — しない（決定 6）

## NAS の共有フォルダ（SMB）

- 依存は smbj（Apache-2.0）と、推移的な asn-one（Apache-2.0）・mbassador（MIT）・bcprov-jdk18on（Bouncy Castle Licence）で、MPL-2.0 で公開する方針（ADR 0012）とは食い違わない（どれも寛容なライセンス。ライセンスは各 POM の記述による）

## 端末のフォルダ

1. 端末のフォルダも、ほかの取得元と同じくアプリの領域にコピーしてから再生する（決定 6）。その場で再生する形と、元のファイルを消す形は採らない。主に想定する人（PC で録ったファイルを Syncthing-Fork や FolderSync で端末のフォルダに同期して溜めている人）では、消すと同期で元のファイルまで消えるおそれがあり、その場で再生する形は手元のファイルを前提にした箇所の改修が大きいため
2. 構成は NAS の共有フォルダ（SMB）と同じ 3 段（ADR 0013）
3. 選べるのは端末のストレージ（内部ストレージと SD カード）のフォルダだけ。ほかの provider（Google ドライブ、SAF 経由の SMB など）は選び直させる
4. 取得元が端末のフォルダのときは、ダウンロードと同期（定期・手動）にネットワークの条件をかけない（決定 10 の例外。手動の同期の従量制での中止もかけない）
5. 永続権限が無い・取り消された、または選んだフォルダ（根）が無いと分かったら、未接続（ログアウトの状態）にしてフォルダを選び直させる。「分かった」とするのは確かな証拠があるときだけで、それ以外の失敗は SMB と同じく通常の失敗（到達不能）に倒す。手元の番組・各回・ファイルは残す（取得元 ID は相対パスなので、選び直したフォルダの中の構成が同じなら結び直る）。根が無いのを「無い」で返すと全番組が消失扱いになるので、認証の失敗として扱う
6. 「取得元を変える」では、持っている永続権限を手放す
7. `ACCESS_LOCAL_NETWORK` は、取得元が Jellyfin か SMB のとき（ログアウト中で前回の取得元が Jellyfin か SMB のときを含む）だけ起動時に要求し、まだ取得元を選んでいない人には取得元の選択で Jellyfin か SMB を選んだときに要求する。端末のフォルダの人には要求しない
8. 選ぶときは、取得元の選択の「端末のフォルダ」から説明の画面（3 段の構成の例と、内部ストレージの直下や Download そのものは選べないこと。`docs/ui.md`）を経て、OS のフォルダ選択を開く。選んだ後は SMB と同じく直下が読めるかだけを確かめて保存する

- 依存は足していない（SAF の標準の API だけを使う）
- SAF の実機の挙動（`Download` の下のサブフォルダを選べるか、SD カードのツリーの URI の形と authority、フォルダの中のファイルが多いときの遅さ）は確かめていない（未確認）
