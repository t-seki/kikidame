同期（`planSync`）は「取得元の一覧に無い、取得元 ID を持つ各回は手元から削除する」規則を持つため、入力に渡す一覧が不完全だと、載っていないだけの各回を誤って削除する。そのため**削除の権限を持つ入力は完全な一覧だけ**とする。

## 決定

1. **ライブラリ全体の同期**は、必ずライブラリ全体の完全な一覧（全走査。取得元の境界、ADR 0007）を入力にして `planSync` を回す。全走査には番組一覧も付いてくるので、`Gone`（番組が取得元の番組一覧に無い）もここで判定する
2. **1 番組の同期**は、その番組の各回の一覧（番組単位の取得）を入力にする。その番組についての一覧は完全なので、その番組の中では削除の権限を持つ。ほかの番組には触れず、最終同期の時刻も更新しない。同期を OFF にした番組でも同じで、固定していない手元のファイルは消える（同期対象でない番組は、固定した回だけを手元に置くため。CONTEXT.md「固定」）
3. 番組単位の取得は、番組が無くても空の一覧を返すことがある。そのため 1 番組の同期では、先に番組そのものが取得元にあるかを確かめ、無ければ `Gone` として判断保留にする
4. **共有フォルダの全走査は番組ごとに取り込む**。一覧（名前・大きさ・更新日時）を先に全部取り、タグを読み終えた番組から 1 番組ずつ取り込み、その番組の中で削除・予約する（1 番組の同期と同じ範囲）。番組の消失の判断と最終同期の時刻の記録は、全部を読み終えたときだけ行う。Jellyfin の全走査は番組ごとに取り込まない
5. 全走査が失敗したときは `planSync` を呼ばずに終える（何も落とさず何も消さないので、全番組を判断保留にしたのと同じ結果になる）。番組ごとに `Unavailable` を渡す経路は今は無い。`planSync` の入力の型としての `Unavailable` は、番組単位の取得をライブラリ全体の同期に使う日のために残す
6. 全走査は、定期の同期とアプリを開いたときに走る（周期は `docs/architecture.md` の「同期エンジンの設計」）。全走査をこの頻度で回しても許容できる重さだと判断した

## 共有フォルダの全走査を番組ごとに取り込む理由

大きな共有では、全部のファイルの一覧とタグを読み終えてからまとめて取り込む形だと、タグの読み取りの途中で接続が切れたときに何も取り込まれない。番組ごとに取り込めば、止まって失うのは読みかけの番組 1 つ分になる。

- タグを読むのは、新しいファイル、またはパス・大きさ・更新日時のどれかが変わったファイルだけ（ADR 0007 の決定 8）。取り込み済みの回は大きさと更新日時を手元に持つので、次の同期ではタグを読まず、続きから読める。そのための別の控えは作らない
- 仮のタイトルで取り込むことはしない
- タグの読み取りは、遅いのは転送量ではなく往復の回数と見て、ファイルごとにまとめて読んで往復を減らす。並列で読むことはしていない。読み方・張り直し・進み具合の表示は `docs/architecture.md` の「共有フォルダの走査」節

走査の途中で画面が消えて裏に回ると、しばらくして Android が接続を壊し、張り直しも効かずに到達不能で終わることがある。壊されるまでの時間は一定ではなく、何で決まるかは未確認。取り込み済みの番組は残り、次の同期で続きから読む。

## 確かめた事実

- Jellyfin の音楽のライブラリでは、番組があるかを `/Items/{id}` では確かめない。`/Items/{id}` は `MediaSources` を含む全部の欄を返し、SDK 1.9 は `MediaStream.IsOriginal` を必須と見なすので、それを返さないサーバの応答ではデコードが落ちる。番組の id を絞り込みにした一覧の検索（空なら消失）で確かめる

## 退けた案

- **差分取得**（`DateCreated` の降順で取り、手元の最大の取り込み日時で打ち切る。ふだんは差分、1 日 1 回は全走査）— 打ち切りより前の各回が一覧に載らないので `Known` として渡せない。全走査をこの頻度で回せる今は、取り込みだけを行う経路を別に持つ価値は無い。要るときは「取り込みだけを行い、削除はしない入力」として設計する
- **番組単位の取得をライブラリ全体の同期の入力にする** — 同期対象の番組の数だけ要求すれば軽いが、番組一覧が無いので `Gone` が出せず、同期対象でない番組の各回の一覧が古いまま残る
- **共有フォルダの全走査で、全部のタグを読み終えてからまとめて取り込む** — 上のとおり、途中で接続が切れると何も取り込まれない
