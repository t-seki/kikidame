手元のファイルは、取得元のファイルの版が変わったら**差し替える**（CONTEXT.md）。取得元の種類（Jellyfin の音楽とブックのライブラリ、共有フォルダの SMB と端末のフォルダ）によらず同じ規則にする。

取得元のファイルは、落とした後に書き換わることがある。たとえば録音ツールの rajikura は、radiko の AI チャプターがまだ取れないとチャプター無しでファイルを出し、後で取り直して同じファイルに書き足す（t-seki/rajikura#425）。一度落とし終えた回（`local_files.state = DONE`）を替えないと、書き足しの前に落とした端末ではチャプターが出ない。

## 決定

1. 手元にある回のファイルが取得元で書き換わったら、同期のときにそれを見分けて、新しいファイルに差し替える
2. 書き換わりを見分ける値を**ファイルの版**と呼び、手元の回ごとに**落としたときの版**を持つ。共有フォルダの版はファイルの大きさと更新日時の組、Jellyfin の版は各回の一覧の `Etag`（`ItemFields.ETAG` を求めたときだけ返る）。記録するのは、そのダウンロードを予約したときに一覧で見た版（落とし始めた後に取得元が変わっても、次の同期で差し替えに回る。余計に 1 回落とすことはあっても、取りこぼさない）
3. 見分け方:
   - 共有フォルダは、一覧の版が落としたときの版と違えば差し替える
   - Jellyfin は、一覧の `Etag` が落としたときの版と違う回だけ、取得元のファイルの大きさを 1 回問い合わせる。手元のファイルの大きさと違えば差し替え、同じなら差し替えずに新しい `Etag` を版として書く。一覧の `Etag` が null の回は、比べず、版も書き換えない
   - 大きさの問い合わせは、取得元の境界（`SourceGateway`、ADR 0007）の口で行う
4. 版を持たない手元の回は、最初の同期で 1 回だけ大きさで比べ、違えば差し替え、同じなら今の版を書く
5. 差し替えの対象は、手元にある回なら種類によらない（保持している回、固定した回、同期対象でない番組で手で落とした回、再生済みの回）。ただし**聴いている回**は、その同期では差し替えを予約せず、聴いている回でなくなった後の同期で予約する
6. 差し替えの間:
   - 落とし終えるまで、今のファイルで聴ける。表示も「手元にある」のまま
   - 差し替えは古い版の書きかけの続きを要求せず、頭から落とす
   - 失敗したら、今のファイルと落としたときの版をそのまま残し、次の同期でまた見分けて予約する
   - 差し替えの間にその回を消すとき（保持ルール・手の削除）は、差し替えも取り消す
   - 落とし終えた時点でその回が聴いている回になっていたら、差し替えずに書きかけを捨てる（次の同期でまた予約する）
   - 落とし終えたら、今のファイルを差し替え、版と大きさを新しい値にする
7. 再生位置と再生済みは、差し替えでは変えない
8. 差し替えのダウンロードも、普通の同期のダウンロードと同じ待ち行列と条件（「Wi-Fi のみ」の設定など）で落とす

## Jellyfin で、`Etag` を合図にして大きさで確かめる理由

- Jellyfin の `Etag` の中身は `DateLastSaved` の MD5 だけで、ファイルの大きさや更新日時は入っていない（jellyfin/jellyfin の `BaseItem.cs`。v10.11.11 などのソースで確かめた）。なので、メタデータや画像を保存し直しただけでも値が変わる（偽陽性）。`Etag` だけで差し替えると、中身の変わらない回まで差し替えることになる
- ファイルの大きさと、更新日時から作る `ETag` は `MediaSourceInfo` にしかない。`MediaSources` は SDK 1.9 だと 10.11 の応答を読めずに落ちるので、求めない（`docs/architecture.md` の「ライブラリ構造のマッピング」）
- 大きさは `/Items/{id}/Download` に `Range: bytes=0-0` を付けた 206 の `Content-Range` の全長から取れる。`HEAD` は 405 で取れない。どちらも 10.10.7 と 12.0 のテストサーバで確かめた。取得元のファイルを書き換えた後、Jellyfin が走査し直す前でも、ディスク上の今の大きさが返った（同じく両方の版で確かめた）
- `Etag` は走査で書き換わりに気づいたときに変わる。テストサーバで、ファイルを書き換えて走査させると変わり、書き換えずに走査させ直すと変わらなかった（10.10.7 と 12.0）
- 大きさを変えない書き換えは拾えない（対象にしない）。チャプターの書き足しでは大きさが変わる

## 選ばなかった案

- **`Etag` だけで差し替える**: メタデータの保存だけで変わる（上）ので、中身の変わらない回まで差し替える
- **同期のたびに全部の回の大きさを問い合わせる**: 手元の回の数だけ毎回問い合わせが要る。`Etag` が変わった回と版を持たない回に絞れば、ふだんの同期では問い合わせない
- **`MediaSources` を求める**: SDK 1.9 が 10.11 の応答を読めずに落ちる
- **手の操作で差し替える**（各回のシートの「差し替える」など）: 書き換わりに利用者が気づく手がかりが無い
- **聴いている回を、プレイヤーに載せたまま差し替えて読み込み直させる**: 聴いている最中に音が途切れる。載せたままファイルだけを替えると、プレイヤーがシークなどで同じパスを開き直したときに古いファイルの目次で新しいファイルを読み、音が化けたり再生に失敗したりしうる（推測。media3 のソースでは確かめていない）

## 結果

- Room の版 11 で、`episodes.sourceVersion`（一覧で最後に見た版）と、`local_files.sourceVersion`（落としたときの版）・`replaceState`・`replaceVersion`（差し替えの状態）を持つ。差し替えの間も `local_files.state` は DONE のまま
- 取得元の境界（`SourceGateway`）に、各回のファイルの大きさを取る口（`fetchFileSize`）がある。ダウンロードの実行側（`DownloadQueue`）に差し替えの口（開始・完了・断念・まだ要るか・残った実行中の戻し）を、利用者側（`DownloadRepository`）に差し替えの予約（`enqueueReplacements`）を持つ
- 差し替えの予約は、同期の結果の予約数（`RefreshResult.enqueued`）に含め、同期の文言でも「N 回をダウンロード予約」として数える
- 手元の大きさは、ディスク上のファイルの長さで比べる。共有フォルダでは `episodes.sizeBytes` が走査のたびに一覧の値で上書きされるため
- 端末のフォルダで provider が更新日時を返さないときは、エポックで補う（`DeviceFolderTree`）。そのとき版は大きさだけで決まるので、大きさの変わらない書き換えには気づけない（差し替えない）
- Jellyfin で書き換えに気づくまでの遅れ（ライブラリの走査は既定でおよそ 12 時間ごと）は縮めない
- 形と流れは `docs/architecture.md` の「差し替え」節
